# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DarwinForge — a macOS-only app to control, author motion for, and program two ROBOTIS
DARwIn-OP units over USB serial: 1st-gen OP1 (CM-730) and 2nd-gen OP2 (CM-740).
Unofficial; not affiliated with ROBOTIS. Apache 2.0.

Core stack: **Rust core (`app/core/`) + SwiftUI (`app/ui/`)**, bridged via a C FFI
header generated by cbindgen and vendored into the Swift package. A separate iOS
companion app lives in `app/mobile/`. See `docs/decisions/` (ADR-009..013) for the
boundary rationale.

## Build & run (macOS)

```sh
make doctor          # tool check (git/python3/node/cargo/rustc/swift)
make run             # build Rust core → swift build → swift run DarwinForgeApp
make app             # build without running
make test            # cargo test --workspace  (Rust only)
make lint            # cargo fmt --check + cargo clippy -D warnings
make headers         # regenerate forge-ffi/forge_core.h.in via cbindgen
make clean
```

The build pipeline is `scripts/build-mac.sh`: it builds the Rust static lib, runs
cbindgen, and fills `app/ui/DarwinForge/Vendor/CForgeCore/{lib,include}` that the
Swift package links against. Flags: `-u` universal (arm64+x86_64), `--swift` also
`swift build`, `--run` then run, `--skip-rust` reuse existing Vendor/.

**Mic / TCC features must run as a real .app bundle**, not `swift run` / `make run`
— `swift run` has no Info.plist, so pressing the mic triggers a TCC crash. Use
`bash scripts/run-app.sh`, which packages the binary into `.build/DarwinForge.app`
with a proper Info.plist and `open`s it.

### Tests — a single test

```sh
cargo test -p forge-core --manifest-path app/core/Cargo.toml synth::      # Rust, by path
swift test --package-path app/ui/DarwinForge --filter VirtualJoystickMapperTests
```

Swift tests must run **serially** (no `--parallel`): several tests share
process-global `UserDefaults.standard` keys (`mobileRelay.preferredHost`,
`df.walklab.*`, harness toast flags) and cross-contaminate when parallel. CI runs
plain `swift test`. If you add a test that writes UserDefaults, expect flakiness
under parallel runs.

## CI (.github/workflows/ci.yml)

Runs on PR/push to `main`. `rust` job (ubuntu): `cargo fmt --check`, clippy `--lib`
strict (`-D warnings`) + all-targets warn-only, build, test. `swift` job (macos-14,
needs rust): selects `latest-stable` Xcode (default 15.x miscompiles some Sendable /
MainActor concurrency patterns), builds the Rust vendor lib, then `swift build` +
`swift test`. `RUSTFLAGS: -D warnings` globally.

## Hardware safety (real robot)

The CM-740 (OP2) firmware is **not pin-compatible** with the CM-730 (OP1) — never
cross-flash. Before any motion authoring: cradle in the maintenance stand, disable
leg torque (`disableTorque(.leftLeg, .rightLeg)`), keep a battery disconnect in reach.
`forge-cli motion play` defaults to dry-run; `--engage` actually sends to the robot.

## Connection modes (mutually exclusive)

The CM730/740 serial line is shared, so walking and joint-editing are exclusive
modes. Studio/Teach need joint-edit (bus) mode; walking needs walk mode. A toolbar
one-click switcher handles the transition (commit 960afb3). When telemetry lags, the
wired `192.168.123.1` path is ~166× faster than the wireless path — the poller can
get stuck on wireless, so an app-driven "wired" reconnect matters.
