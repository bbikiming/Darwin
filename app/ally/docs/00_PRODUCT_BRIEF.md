# DARwIn FPV — 제품 기획서 (Product Brief)

- 작성일: 2026-06-13
- 대상 기기: ASUS ROG Ally (Windows 11, 7" 1080p 120Hz 터치, 내장 XInput 패드, Ryzen Z1 Extreme / 16GB)
- 제품명: **DARwIn FPV** (실행 파일 `darwin-fpv`, 폴더 `app/ally/`) — D4 확정
- 기술 스택: **Tauri 2 하이브리드** (Rust 백엔드 = 안전·통신 전담, WebView2 = 표시 전용) — D1 확정
- 조종 매핑: **RG G01 실기 검증 수치 1:1 동결** — D2 확정 (변경 시 실기 재검증 필수)
- 상태: 기획 확정. 상세 설계는 `app/ally/docs/` 후속 문서(아키텍처·UX·웨이브 계획) 참조
- 작성 기준: 이 리포 `docs/design/README.md`의 "다른 세션이 추가 탐색 없이 착수 가능"

> **확정 결정(D1·D2·D4)은 사용자 승인 완료 — 본 문서에서 재론하지 않는다.**
> 와이어 프로토콜의 단일 진실원은 `docs/ssh-parity-contract.md` — 본 문서는 요약만 인용하며,
> 수치가 충돌하면 계약 문서가 이긴다.

## §0. TL;DR

**게임을 실행하듯 DARwIn FPV를 켜면 90초 안에 라이브 카메라를 보며 다윈을 조종한다 —
시뮬레이터 게임의 몰입감과 실기 로봇의 안전 계약을 동시에.**

DARwIn FPV는 ROG Ally용 DARwIn-OP2 원격 조종 네이티브 앱이다. 이 리포에서 실기 검증된
세 조상 — Mac DarwinForge 콕핏의 HUD 문법, RG G01 직결 파일럿의 조종 매핑 수치,
Switch 웹 콕핏의 레이아웃·자산 — 을 그대로 계승하고, 와이어 계약(`docs/ssh-parity-contract.md`)을
한 글자도 재발명하지 않는다. Ally가 처음 더하는 것은 **"게임기에서 게임처럼"** —
Armoury Crate 게임 패키징, 게임패드 퍼스트 내비게이션, 출격 시퀀스 연출, 사운드·햅틱,
1080p 토큰 스케일, 유선 직결 모드 UI다. 안전 계약(E-STOP rising-edge 즉시발화,
3티어 failsafe, 무선 정지 ≤320ms)은 연출보다 항상 위에 있다.

```
[ROG Ally: darwin-fpv]                        [DARwIn-OP2: walklab 브로커리지]
 Rust 백엔드 ──UDP DFCMD 20Hz──────────────▶ :17374 (명령, 14-token v1)
 (gilrs 250Hz │─UDP DF-ESTOP ×3연발─────────▶ :17372 (E-STOP, 0/50/100ms)
  폴링·안전   │◀─UDP TEL2 30Hz──────────────  → 클라이언트 등록 포트 (기본 :17371)
  게이트)     │─SSH (핸드셰이크·파일 폴백 5Hz)─▶ /tmp/df-walklab-{channel,cmd,estop}
 WebView2 ◀──│ (표시 전용 — 명령 생성·E-STOP 경로 비관여, INV-2)
 풀스크린 UI  └◀─MJPEG http://robot:8080────── 카메라 (320×240, 보행 중 ~8–15fps)
```

## §1. 배경 — 검증된 세 조상

DARwIn FPV는 백지에서 출발하지 않는다. 이 리포에는 같은 로봇을 세 갈래로 조종해 본
실기 검증 기록이 있고, 각 갈래가 서로 다른 것을 증명했다. Ally는 이 셋의 교집합이
아니라 **합집합을 한 기기에서** 구현하는 첫 시도다.

> 비유: 세 조상은 각각 "계기판 설계도"(Mac), "검증된 운전 감각"(G01), "이식 가능한
> 차체"(Switch)를 남겼다. Ally는 이 셋을 한 차에 조립하고 게임기 외장을 입힌다.

| 조상 | 무엇이 검증됐나 | 어디까지 도달했나 | 근거 (파일/보고서) |

## §3. 포지셔닝 지도 — 4기기 역할 분담

DARwIn FPV는 기존 기기를 대체하지 않는다. 각 기기의 확정 역할:

| 기기 | 역할 | 담당 | 비유 |
|---|---|---|---|
| **Mac DarwinForge** | **작업장** | 모션 저작·Teach·Synth·WalkLab 튜닝·시리얼 직결(bus) 관절편집 — 만들고 고치는 모든 것 | **정비 격납고** — 기체를 뜯고 조립하는 곳 |
| **Ally DARwIn FPV** | **조종석** (본 제품) | 무선 FPV 조종·현장 데모·거실 주행·유선 직결 디버깅 — 타고 나가는 모든 것 | **출격 콕핏** — 정비가 끝난 기체로 비행하는 곳 |
| **RG G01 직결** | **최저 레이턴시 백업** | 로봇 USB 동글 직결(온보드 GamepadPilot) — 네트워크 0홉, Ally·Mac 전부 꺼져 있어도 동작. H0~H3 트랙 별도 유지 (§7 비목표) | **유선 백업 조종간** — 전자장비가 다 죽어도 잡아당기면 움직이는 케이블 |
| **Switch 웹 콕핏** | **레거시** | 유지보수 모드 — 신규 개발 동결. 와이어 구현(`df_udp.py`)·매핑 식·콕핏 자산은 Ally가 계승 | **퇴역 예정 기체** — 부품(설계 유산)은 차세대로 이식 완료 |

경합 규칙: 로봇은 단일 공유 자원이다(메모리 `robot-session-contention` 참조). Ally와
Mac이 동시에 명령을 보내는 상황은 로봇측 O1 latest-wins 슬롯과 `active_source`
표시(TEL2 필드)로 가시화되며, G01 로컬 입력은 1s 신선도 우선권(`GP_LOCAL_FRESH_MS`)을
가진다 — Ally UI는 `active_source != udp`일 때 "조종권 없음"을 명시 표시해야 한다.

| ② | **게임패드 퍼스트 포커스 내비** | 전 화면·전 메뉴를 패드만으로 항행(포커스 링·방향 이동·A 결정/B 취소). 터치는 보조 입력. **예외: E-STOP만 패드+터치 이중화** — 화면 모서리 상시 터치 타깃 | 세 조상 모두 해당 없음: Mac=마우스, Switch=터치 키오스크, G01=무화면. §5-④의 구현체 |
| ③ | **출격 시퀀스 연출** | ARM 의식의 게임화: 접속→핸드셰이크→캘리브레이션 확인→ARM을 "출격 체크리스트" 연출로 감싼다. **안전 계약 그대로** — 연출은 진입 단계에만, ARM 임계 0.80·E-STOP 경로는 비연출(§5-①) | 선례 3종 전부 기능적 진입만 존재. 몰입(S2)과 데모 효과(S1)를 동시에 만드는 Ally 고유 레이어 |
| ④ | **사운드·햅틱** | 보행 위상(TEL2 phase) 동기 햅틱, ARM/E-STOP/failsafe 상태 전환음, 낙상 리스크(risk 필드) 경고음. 선례 3종 전부 무음이었다 | Ally 내장 패드 진동 + 스피커 + TEL2 30Hz 실시간 phase = 셋 다 갖춘 첫 기기 |

## §5. 제품 원칙 5

설계·구현 중 분쟁이 생기면 이 5개 원칙이 심판한다. 각 원칙에 실제로 일어날 분쟁
예시를 1개씩 붙인다.

### 원칙 1 — 안전 계약은 연출보다 위에 있다

E-STOP·failsafe 경로에 애니메이션·디바운스·확인 다이얼로그·트랜지션을 끼워 넣지
않는다. E-STOP은 rising-edge 즉시발화(Rust 백엔드, webview 비경유 — INV-2)이며,
화면이 뭘 그리고 있든 발화한다. G01 브링업의 교훈 "ACK≠서보 기록"을 UI로 확장하면:
**"발화 연출≠실제 발화" — 표시는 발화의 결과이지 조건이 아니다.**

> **분쟁 예시**: "E-STOP을 누르면 화면이 빨갛게 슬로모션 셰이크되는 연출을 넣자.
> 멋있고 데모 효과도 좋다." → 연출 자체는 허용(발화 *후* 표시 레이어). 그러나 연출
> 로직이 E-STOP 송신과 같은 스레드/프레임 루프에 있거나, 연출 완료를 기다려 송신하면
> **기각**. 송신은 입력 스레드에서 즉시, 연출은 그 결과 통지를 받아 그린다.

### 원칙 2 — 검증된 손맛을 보존한다

G01 매핑 수치(§4.1)는 2026-06-13 실기 입회로 확정된 조종감이다. "Ally 스틱이 더
좋으니 곡선을 부드럽게" 같은 개선 제안은 수치 변경 = **실기 재검증**을 비용으로
지불해야 한다(D2). 와이어 계약도 동일 — 로봇측 변경 없이 클라이언트만 추가한다.

> **분쟁 예시**: "Ally 홀 센서 스틱은 드리프트가 없으니 데드존을 0.10→0.05로 줄여
> 미세 조작감을 높이자." → 합리적 가설이지만 **수치 변경이므로 실기 재검증 게이트
> 통과 전 기각**. 절차: 기본값 0.10 동결 출시 → 디버그 모드(S3)에서 실험 프로파일로
> 측정 → 실기 검증 보고서 작성 후에만 기본값 승격.

### 원칙 3 — 게임처럼 시작하고, 계기판처럼 보여준다

연출의 자리는 진입(부팅·접속·출격 시퀀스)이고, 운용 화면의 자리는 정보 밀도다.
조종 중 HUD는 Mac 콕핏 문법(모노스페이스 readout, 상태 5줄, 래치 인디케이터)을
따른다 — 운용 화면에서 장식이 데이터를 밀어내면 안 된다.

> **분쟁 예시**: "조종 중에도 게임처럼 점수·콤보·이펙트를 띄우자, S2 몰입에 좋다."
> → 운용 HUD의 정보 슬롯(속도게이지·래치·상태블록)을 잠식하면 기각. 게임화 요소는
> W4(게임화 웨이브)에서 *별도 오버레이 토글*로, 기본 OFF, E-STOP·failsafe 표시를
> 가리지 않는 영역에만 허용.

### 원칙 4 — 양손은 그립에서 떨어지지 않는다

전 조작이 게임패드로 완결된다(§4.2 ②). 터치는 보조이고 키보드는 존재하지 않는
것으로 취급한다(S1 무키보드 요구). 어떤 플로우든 "이 단계는 터치로만 가능"이
발견되면 그것은 버그다. 유일한 의도적 예외는 E-STOP 터치 이중화 — 손을 *더하는*
것은 허용, 손을 *요구하는* 것은 금지.

> **분쟁 예시**: "WiFi 비밀번호 입력은 어차피 OS 키보드가 필요하니 설정 화면은
> 터치 전제로 만들자." → 기각. 네트워크 설정은 사전 프로비저닝(설정 파일·QR·OS
> 레벨)으로 앱 밖에 두고, 앱 내 설정은 전부 패드 항행 가능한 선택지로 구성한다.
> OS 키보드가 불가피한 항목은 "최초 1회 설정"으로 격리하고 데모 플로우(S1)에서 제거.

### 원칙 5 — 정직한 표시

합성 포즈는 "합성"임을, 추정치는 추정임을 라벨로 밝힌다. TEL2에는 관절각이 없다 —
3D 뷰는 phase 기반 FK + IMU 보정의 **합성 포즈**이며(Mac과 동일 방식), 화면에
"SYNTH" 라벨을 상시 표시한다. 레이턴시·전압·낙상 리스크도 측정치와 추정치를
시각적으로 구분한다. G01 브링업 게이트 ②의 정정 사례(— "1-2ms PASS"를 "flag 생성
지연 ≤2ms, 물리 정지는 미계측"으로 고쳐 씀)가 이 원칙의 표준이다.

> **분쟁 예시**: "3D 로봇이 실제와 똑같이 움직이는 것처럼 보이는데 SYNTH 라벨이
> 몰입을 깬다, 빼자." → 기각. 라벨 디자인을 덜 거슬리게 다듬는 것은 허용하되 제거는
> 불가 — 합성 포즈는 낙상·걸림 같은 실제 자세 이상을 *보여주지 못하며*, 사용자가
> 3D를 실측으로 오인하면 카메라 확인을 생략하는 안전 문제로 이어진다.

## §6. 성공 지표

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| **Time-to-teleop** | **≤90s** (Ally 전원 → ARM 완료) | 스톱워치 10회 측정, **중앙값**. 콜드부팅 포함, 네트워크 사전 프로비저닝 상태 기준 |
| **무키보드 데모 완주율** | **100%** | S1 시나리오 전 플로우(부팅→접속→ARM→주행→E-STOP→복구→종료)를 패드+터치만으로. 키보드·마우스·터미널 개입 1회라도 발생 = 실패 |
| **입력→로봇 무선 레이턴시** | **p95 ≤400ms** | 입력 타임스탬프 → TEL2 `seq_applied` 회신 왕복으로 산출(자체 `cmd_id` 시퀀스 대조). 무선 192.168.0.33 경로, 보행 중 측정 |
| **E-STOP 정지** | **≤320ms** (기존 무선 계약) | `docs/ssh-parity-contract.md`의 기존 검증 절차 재사용(UDP ×3연발 + 파일 + 워치독). Ally 클라이언트가 계약을 *깨지 않음*을 확인 — 신규 계약 아님 |
| **UI 프레임레이트** | **60fps ≥99%** (조종 세션 중) | WebView2 프레임 통계 또는 캡처 분석. 카메라 스트림 + HUD + (3D off) 기준, 10분 세션 |
| **배터리 연속 조종** | **≥2.5h** (Ally 40Wh) | 무선 조종 + 카메라 + 햅틱 ON, 화면 밝기 데모 수준 고정, 만충→경고까지 |
| **E-STOP 드릴** | 신규 사용자가 설명 10초 후 **3초 내 발화** | 처음 잡는 사람에게 "빨간 버튼(B) 또는 화면 모서리"만 안내 → 보행 중 "정지!" 신호 → 발화까지 시간. 5인 전원 통과 |

지표의 우선순위 = 표 순서. Time-to-teleop과 무키보드 완주가 S1(1순위 시나리오)을
직접 측정하고, 레이턴시·E-STOP은 안전 계약 준수를, 나머지가 S2 품질을 측정한다.
