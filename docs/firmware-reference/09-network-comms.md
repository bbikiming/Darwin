# 09 — Network & Communications (ROBOTIS-OP2 Factory Firmware)

> **PRIVACY**: All credentials (WPA PSK, SSH private keys) are redacted from this document. Only public information and fingerprints are quoted. No private key bytes were copied. No WPA passphrases exist on this image (no `wpa_supplicant.conf` was present).

## TL;DR

The robot ships with hostname `robotis`, a single statically-configured wired interface `eth0` at `192.168.123.1/24` (no gateway, no DNS), and `sshd` listening on the default port 22 with `PermitRootLogin yes` and password authentication (the default `PasswordAuthentication yes`). **No WiFi network was pre-configured** — the `wpa_supplicant` package is installed but the directory contains only ifupdown helper scripts, no SSID/PSK configuration. The factory image therefore expects the operator to plug in an Ethernet cable to the OP2's on-board NIC and talk to it at `192.168.123.1`.

## Network interfaces

### `/etc/network/interfaces`
```
auto lo
iface lo inet loopback

auto eth0
iface eth0 inet static
  address    192.168.123.1
  netmask    255.255.255.0
  broadcast  192.168.123.255
  network    192.168.123.0
```

Identification:

| Interface | Role | Configured | Notes |
|-----------|------|------------|-------|
| `lo` | Loopback | Auto | Standard |
| `eth0` | Wired | **Static, `192.168.123.1/24`** | No `gateway`, no `dns-nameservers`. Host-side bring-up only. |
| `wlan0` | Wireless | **Not declared** | The kernel will see the card if present, but ifupdown will not auto-configure it — managed externally by NetworkManager or `wpa_supplicant` if the user adds a config. |

The static `192.168.123.0/24` choice is the standard ROBOTIS factory subnet — the user plugs a laptop directly into the OP2, gives their laptop something like `192.168.123.100/24`, and SSHes to `192.168.123.1`. There is no DHCP server on the robot (the `dhcpd.conf` present in `/etc/dhcp/` is the unmodified package default and there is no `isc-dhcp-server` configured to start). The DHCP **client** package is installed (`dhclient.conf` is the unmodified Debian sample), but it is unused because `eth0` is `inet static`.

## WiFi configuration

**No WiFi was pre-configured on the factory image.**

`/etc/wpa_supplicant/` contains only the helper scripts shipped with the `wpasupplicant` package:

```
/etc/wpa_supplicant/action_wpa.sh
/etc/wpa_supplicant/functions.sh
/etc/wpa_supplicant/ifupdown.sh
```

There is **no `wpa_supplicant.conf`**, no `wpa_supplicant-wlan0.conf`, no `system-connections/` entries for NetworkManager (the `/etc/NetworkManager/system-connections/` directory is empty), and no SSID/PSK stored anywhere on disk. Therefore there is **nothing to redact** in this section — there are no credentials.

NetworkManager is installed but configured **not to manage ifupdown interfaces**:

`/etc/NetworkManager/NetworkManager.conf`
```
[main]
plugins=ifupdown,keyfile
dns=dnsmasq

[ifupdown]
managed=false
```

With `managed=false`, NetworkManager hands `eth0` off to the static config in `/etc/network/interfaces` and only handles any interfaces NM would discover dynamically (e.g., a USB WiFi adapter — but none was pre-paired).

`/etc/dbus-1/system.d/wpa_supplicant.conf` is the unmodified package D-Bus policy file — it grants `root` and the `netdev` group access to `fi.w1.wpa_supplicant1`. Informational, not load-bearing.

**Practical implication**: out of the box, the robot is reachable only via wired Ethernet. To bring up WiFi, a user would create `/etc/wpa_supplicant/wpa_supplicant.conf` themselves (or use NetworkManager's `nmcli`/`nm-applet`) — the factory image does not pre-populate any RoboCup/lab SSID.

## DNS resolution

`/etc/resolv.conf` is a symlink to `../run/resolvconf/resolv.conf` (dynamic, regenerated at boot by `resolvconf(8)` from `/etc/resolvconf/resolv.conf.d/` snippets).

| File | Content |
|------|---------|
| `/etc/resolvconf/resolv.conf.d/head` | Header comment only — `# Dynamic resolv.conf(5) file ... DO NOT EDIT THIS FILE BY HAND` |
| `/etc/resolvconf/resolv.conf.d/base` | **Empty** (zero bytes) |
| `/etc/resolvconf/interface-order` | Default ordering: `lo.inet* > lo.dnsmasq > tun* > tap* > eth* > ath* > wlan* > ppp* > *` |

With an empty `base` and no DNS push from DHCP (because `eth0` is static), the runtime `/etc/resolv.conf` will be effectively empty unless the operator runs `dhclient` on another interface or appends something to `base`. NetworkManager's `dns=dnsmasq` plugin would normally inject a `nameserver 127.0.0.1` and run `dnsmasq` as a local resolver, but with `ifupdown` set to `managed=false` for the wired interface, this only matters when a WiFi connection or DHCP-managed interface comes up.

In practice, the factory robot does **not need to resolve external hostnames** for any of its work — the only networking it does is "be reachable on the LAN for SSH and Game Controller UDP."

Notes:
- The DSA fingerprint was computed manually (Python `hashlib`) over the base64-decoded `ssh-dss` blob — modern OpenSSH (>= 8.x on the documenting machine) refuses to read DSA pubkeys with `ssh-keygen -lf`, but the blob parses cleanly: `algorithm="ssh-dss"`, DSA prime `p` length 1024 bits.
- DSA host keys (`ssh-dss`) are **deprecated** by modern OpenSSH clients (disabled by default since OpenSSH 7.0, 2015-08). A current laptop connecting to the OP2 will negotiate RSA or ECDSA, not DSA.
- The keys were generated at first boot (file mtime `Feb 13 2015`) — they are specific to this individual robot, not factory-shared.

## User SSH config (`/home/robotis/.ssh/`)

**The directory does not exist.** There is no `~/.ssh/` for the `robotis` user on the factory image. Therefore:

- No `authorized_keys` — no pubkey is pre-trusted; remote login is **password-only** out of the box.
- No `known_hosts` — the robot has never SSHed out to anything.
- No `config` — no client-side aliases.

Same for `/root/`: no `.ssh/` directory.

This means anyone with the `robotis` user's password (the factory default, which is documented separately in `02-user-accounts.md`) and network reach to port 22 can log in. The first thing a new operator should do is either disable password auth and add their own key to `~robotis/.ssh/authorized_keys`, or change the default password.

## Firewall

**No firewall rules are configured.** There is:

- No `/etc/iptables/` directory
- No `iptables-persistent` config (no `rules.v4`, `rules.v6`)
- No `ufw` rules in active state
- `/etc/hosts.allow` / `/etc/hosts.deny`: both stock samples (TCP-wrappers not gating anything)

In other words, anything that binds a port (sshd:22, the Game Controller UDP listener on 3838 — see `10-game-controller.md`, the Webots TCP debug ports if you run the simulator side, etc.) is reachable from anywhere on the `192.168.123.0/24` subnet the robot is on.

## Zeroconf / mDNS

The `avahi-daemon` package is installed but **no `avahi-daemon.conf` is present in `/etc/avahi/`** — Avahi will use its compiled-in defaults if it runs (publish hostname as `robotis.local`, listen on all interfaces). The only service file shipped is:

`/etc/avahi/services/udisks.service` — publishes `_udisks-ssh._tcp` on port 22:
```xml
<service-group>
  <name replace-wildcards="yes">%h</name>
  <service>
    <type>_udisks-ssh._tcp</type>
    <port>22</port>
  </service>
</service-group>
```

So when the robot is on a network where avahi is running, peers should be able to discover it as `robotis.local` and as an SSH endpoint via the `_udisks-ssh._tcp` Bonjour record. This is a convenience for "find the robot without knowing its IP" — useful at competition where IPs may be DHCP-assigned by a field router rather than the static `192.168.123.1` here.

## Custom comms (Game Controller, etc.)

The factory image's competition-related comms — RoboCup Game Controller UDP listener — are documented separately in `10-game-controller.md`. From a pure-OS perspective, no custom systemd units, no `xinetd` services, no upstart jobs in `/etc/init/` declare additional listening sockets beyond:

- `sshd` (port 22, tcp)
- `avahi-daemon` (UDP 5353 mDNS; only if the daemon is running)
- `cups` (printing — present but irrelevant for the robot use case)

No DNS daemon (`bind9`, `unbound`) is configured to listen externally. No NTP daemon binds publicly. No HTTP server is installed.

## What this means for the Darwin project

1. **Connectivity model is USB serial, not network.** The Darwin (Mac client) talks to the OP2 over USB to the CM-730 sub-controller — that is the load-bearing channel. The network described above is only for human-operator convenience: SSH into the robot, push code, view logs, run the Game Controller stack.
2. **SSH access plan.** If a user wants to SSH onto the robot: plug an Ethernet cable from the laptop to the robot, set the laptop to `192.168.123.100/24` (any free address in that subnet), then `ssh robotis@192.168.123.1`. Factory password authentication is enabled — the password is documented in `02-user-accounts.md`.
3. **Modern client compatibility.** Modern OpenSSH (>= 8.x) on macOS will refuse the DSA host key but will happily use RSA or ECDSA. No client-side `HostKeyAlgorithms` workaround should be needed.
4. **No WiFi pre-config = nothing to migrate.** When we re-image the OP2 (or build a derivative Darwin firmware), there is no SSID/PSK from the factory that we need to preserve or worry about leaking. The network surface area is small.
5. **Security posture is "lab/competition LAN only".** `PermitRootLogin yes` plus password auth plus no firewall is wide open. Anything based on this image should not be placed on a public network unmodified. If the Darwin project exposes the robot to a less-trusted network, the first hardening pass is: disable root login, switch to pubkey-only, and add a key to `authorized_keys`.
