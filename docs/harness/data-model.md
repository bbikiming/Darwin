# Harness Engineering — Data Model

> Entity definitions used by `HarnessKit` (Swift Package target) inside
> the DarwinForge Mac application. The schema is normalized at the
> **conductor + termination** level so that individual wire failures can be
> logged, queried, and replaced without rebuilding the whole harness record.
>
> The model below is what `HarnessKit` will expose as `@Model` types via
> SwiftData. It is also the schema that `scripts/import_wireviz.py` and
> `scripts/export_wireviz.py` will round-trip with.

## Entities

```
Robot
  id (UUID, PK)
  name                     // "Darwin-1G", "Darwin-2G"
  generation               // enum: OP, OP2
  controller               // FK Controller
  serial_number
  build_date
  notes

Controller
  id
  model                    // enum: CM_730, CM_740
  firmware_version
  port_count               // 6 for both
  pinout_revision          // tracks documented pinout deltas

Joint                      // 20 per robot
  id
  robot_id (FK)
  body_part                // enum: NECK, L_SHOULDER, L_ELBOW, L_HIP, L_KNEE, L_ANKLE, R_*
  axis                     // enum: PITCH, ROLL, YAW
  dynamixel_id             // 1..20
  servo_model              // "MX-28T"
  position_in_chain        // ordinal, for daisy-chain order

Harness                    // a maintainable assembly (e.g. "left-leg-bus")
  id
  robot_id (FK)
  name                     // "LEG_L_BUS"
  description
  drawing_revision
  ipc_class                // 1, 2, 3
  total_length_mm
  installed_at
  expected_service_cycles

HarnessSegment             // physical run between two connectors
  id
  harness_id (FK)
  from_endpoint_id (FK Endpoint)
  to_endpoint_id (FK Endpoint)
  routing_path             // array of joint/landmark IDs traversed
  bend_radius_min_mm
  service_loop_mm
  outer_jacket             // enum: PET_BRAID, HEATSHRINK, BARE, SPIRAL
  length_mm

Conductor                  // one wire inside a segment
  id
  segment_id (FK)
  wire_label               // "W042 LL.KNEE.SIG"
  awg
  insulation               // enum: PVC, FEP, PTFE, SILICONE, TPE
  color
  shielded                 // bool
  shield_termination       // enum: NONE, ONE_END_CTRL, ONE_END_LOAD, BOTH
  signal_type              // enum: POWER_VCC, GND, TTL_DATA, ANALOG, RS485_A, RS485_B, USB_DP, USB_DM, ...
  net_name                 // logical net (e.g. "DXL_BUS_DATA")

Connector
  id
  part_number              // "JST B3B-XH-A", "Molex 5557-04R", or ROBOTIS 3P TTL
  family                   // enum: JST_XH, JST_PH, JST_ZH, MOLEX_MINI_FIT, MOLEX_PICOBLADE, HIROSE_DF13, ROBOTIS_TTL_3P, ...
  pin_count
  pitch_mm
  rated_current_a
  rated_voltage_v
  gender                   // PLUG, RECEPTACLE
  notes

Endpoint                   // one connector instance on the robot
  id
  connector_id (FK Connector)
  location                 // FK to Joint or Controller port
  reference_designator     // e.g. "J3" on CM-730

PinAssignment
  id
  endpoint_id (FK)
  pin_number               // 1..N
  conductor_id (FK)        // null = unused
  function                 // free-text override of net_name when needed

MaintenanceLog
  id
  robot_id (FK)
  harness_id (FK, optional)
  segment_id (FK, optional)
  conductor_id (FK, optional)
  date
  technician
  action                   // enum: INSPECTED, REPLACED, REPAIRED, RE_TERMINATED
  failure_mode             // enum: OPEN, SHORT, INTERMITTENT, INSULATION_DAMAGE, CONNECTOR_BROKEN, STRAIN_RELIEF_FAIL, FATIGUE_BREAK
  root_cause_notes
  cycles_at_failure        // optional, if tracked

TestRecord
  id
  harness_id (FK)
  date
  test_type                // enum: CONTINUITY, HIPOT, IR, PIN_TO_PIN, PULL
  voltage_v                // for hipot/IR
  pass                     // bool
  measured_value           // resistance / leakage
  threshold
  technician
  equipment_serial

PartCatalog                // reusable BOM line items
  id
  manufacturer
  manufacturer_pn
  description
  category                 // CONNECTOR, TERMINAL, WIRE, SLEEVE, HEATSHRINK
  unit_cost
  supplier
  supplier_pn
  datasheet_url
```

## Required UI query patterns

The harness module's view model must support these queries efficiently:

1. **Joint-traversal lookup** — "show every conductor that traverses the L_KNEE joint" — drives the knee-cable replacement workflow.
2. **Lifecycle audit** — "all segments crimped before YYYY-MM-DD."
3. **Reliability trending** — "failure rate by joint over the last 12 months." Will quickly surface the hip-yaw and shoulder-pitch hotspots typical of MX-28 humanoids.
4. **Cross-generation diff** — "diff harness BOM between Darwin-1G (OP) and Darwin-2G (OP2)" so the user can compare what's shared vs unique to each unit.
5. **WireViz export** — "generate WireViz YAML for harness X" so diagrams can be regenerated by the open-source toolchain.

## Wire labelling convention adopted

**Hierarchical primary + numeric ID secondary**, e.g. `W042 LL.KNEE.SIG`.

Format: `<W%03d> <BODY>.<JOINT>.<FUNCTION>`

- `BODY`: `LL` (left leg), `RL`, `LA` (left arm), `RA`, `NK` (neck), `TR` (torso), `HD` (head)
- `JOINT`: per body part — e.g. `HIPY`, `HIPR`, `HIPP`, `KNEE`, `ANKP`, `ANKR`, `SHLP`, `SHLR`, `ELB`, `PAN`, `TILT`
- `FUNCTION`: `SIG` (signal), `PWR` (vcc), `GND`, `RTN` (return), `SHD` (shield drain)

## Workmanship class

The default for both robots is **IPC/WHMA-A-620F Class 2**. A harness can be tagged Class 3 individually (e.g. for show-tour reliability) — the schema's `Harness.ipc_class` field captures this per-assembly.

## Interchange format

**WireViz YAML** is the canonical interchange. Every harness must round-trip without loss through:

- `scripts/import_wireviz.py harness.yaml` → SwiftData store
- `scripts/export_wireviz.py harness-id` → YAML + rendered SVG/PNG

Diagrams produced by WireViz are checked into `docs/harness/<robot>/` for human review.
